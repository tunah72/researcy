# Researcy M1 — Sign-in, Library, and Import

- **Status:** Proposed child specification — awaiting owner approval; not implementation evidence
- **Date:** 2026-09-24
- **Authority:** [System Design revision 2.0](./2026-09-18-researcy-system-design.md) remains normative; [Delivery Map](./2026-09-18-researcy-delivery-map.md) controls status and gates.
- **Milestone:** M1 only. At drafting time Q0 is `Verified`; M1–M5 are `Not started`. Approval of this child specification changes M1 to `Designed`, not `Verified`.

## 1. Outcome and ownership

A person completes real Google sign-in, sees a PostgreSQL-backed Library scoped to that identity, and explicitly imports either an arXiv paper or a supported local PDF. An accepted import has an original immutable PDF in private MinIO storage and a consistent paper/version/queued-job record. **Queued means awaiting M2 processing, not `ready`.** M1 performs only bounded PDF screening; it does not claim full parsing, citations, vectors, or an independently demoable Reader.

| M1 owns | Boundary left to later milestones |
|---|---|
| Next.js landing, sign-in entry, Library and two-option Add paper experience; FastAPI auth/papers/intake endpoints | M3 Reader/Discussion/PDF display; M4 recommendation search; M5 research directions |
| PostgreSQL migrations for users, sessions, papers, original-PDF versions, minimal queued ingestion records, import idempotency, persistent per-user import rate limits | M2 job claim/lease/recovery/retry, parsing and provenance model, embedding, Qdrant, `ready` publication |
| MinIO original-PDF write boundary; official arXiv acquisition; bounded initial PDF checks before acceptance | M2 full document parsing and provenance, final SEC-01 acceptance, deletion cleanup job |
| Cookie sessions, CSRF, owner-scoped queries, logout revocation, request IDs and safe errors | The same security boundary applies to later routes; no second authentication system |

The minimal queued row and migrations are prerequisites for master §8's atomic acceptance contract, **not** completion of delivery-map `JOB-01` or `SEC-01`. M1 does not operate a processing worker; the Library must never show a queued M1 import as successfully processed. Routes listed in master §15 for delete, jobs/retry, conversations, citations, and agents retain their master names and ownership, but their behavior is outside this child specification. A queued item's details may show "Waiting for processing"; no fake retry action is offered. M2 provides actionable failure/retry controls when such states actually exist.

## 2. Decisions and alternative considered

1. **One browser origin, FastAPI as auth authority.** Route `/api/*` and `/auth/*` to FastAPI on the same browser origin as Next.js (reverse proxy/rewrite). Next.js renders pages and makes credentialed browser requests; it never mints application sessions, trusts a client-supplied owner, or exposes MinIO credentials. This avoids cross-site cookie and CSRF complexity. Direct cross-origin credentialed API access is not part of M1.
2. **Accepted imports persist first, process later.** One option was to delay all download/validation/storage until M2's worker. It cannot satisfy the M1 gate requiring a valid original PDF persisted for both import paths. Another was to process synchronously to `ready`; it violates the M2 split. Chosen: bounded initial acquisition and validation in M1; persist the original, then atomically insert paper, source version, and a `queued` job in PostgreSQL and return `202`. M2 later claims that row and owns subsequent stages.
3. **One logical arXiv item per owner and canonical arXiv ID.** Repeating an import of the stored version returns the existing owned item without another PDF or job. An unversioned repeat also returns that item **with its stored version displayed**; it never implies an update to the latest arXiv version. An explicit different `vN` returns `409` with a safe, owner-visible existing-version message; it never silently replaces `active_version` or creates another paper. Reprocessing/version creation belongs to M2. Idempotency keys make interrupted/repeated POSTs return the same resource identity. Uploads are distinct papers unless they repeat the same idempotency key; no global content deduplication.
4. **Initial PDF screening is not full parsing.** M1 may inspect page count, encryption and extractable text in a non-root, time- and memory-limited inspection process, but does not create pages, blocks, spans or chunks. M2's sandboxed full parser must repeat/strengthen checks before processing. M1 never declares a PDF fully supported for exact citations based on this screen alone.

## 3. Component and storage contracts

**Next.js:** Landing exposes Google sign-in. Library is the sole top-level product destination: brand/account access, one `Add paper` action, search by title/author, one list. Add paper offers exactly arXiv URL/ID and PDF upload; no auto-import from paste/navigation or third-party recommendations. Client loads `GET /api/me` and `GET /api/papers` on entry; an untrusted response or URL never determines ownership. State-changing browser calls include cookie credentials, `X-CSRF-Token` read from the CSRF cookie, and an idempotency key for imports. The browser never reads the session cookie or an object-storage key. A protected page redirects to sign-in after `401`; no second Next.js auth provider/session.

**FastAPI:** `auth` verifies OAuth, issues/revokes/resolves sessions, and enforces CSRF. `papers` handles owner-filtered reads, arXiv ID normalization and metadata, upload intake, initial validation, object persistence and atomic acceptance. Both paths share the same validated-PDF acceptance path. Request IDs correlate safe responses and metadata-only structured logs. Never log PDF contents, OAuth tokens, session/CSRF values, object credentials or raw upload data. Persist per-user import rate-limit state in PostgreSQL; no in-memory-only limiter as the sole enforcement.

**PostgreSQL migrations:** Reproducible forward migrations create (a) users keyed by Google issuer + stable `sub`, with display name/email as mutable profile attributes, never email as identity; (b) sessions keyed by a keyed lookup hash, owner FK, CSRF verifier, issue/idle/absolute expiry and revoked state; (c) papers keyed by internal ID and owner FK, source type and canonical arXiv ID where applicable, title/authors/year if available, active immutable source-version reference and acceptance state; (d) document versions keyed by internal ID with owner/paper FK, immutable original PDF SHA-256, private object key, verified byte count/source version, persisted initial-screening warning code when applicable, and pending processing configuration; (e) minimal ingestion job keyed by document version with `queued` stage; (f) owner-scoped idempotency record with operation, request digest and final response identity, plus persistent user-scoped import rate-limit accounting. Foreign keys and unique constraints enforce ownership relationships, one current arXiv source per owner, at most one queued intake per document version, and unique `(owner, idempotency_key)` for import. Never rely on UI filtering or an ID-only `UPDATE`/`SELECT`. M2 extends the job schema for leases/attempts/stages and seals parser/config versions before publication; M1 does not fabricate those values or a `ready` status.

**MinIO:** A private bucket stores exact original PDF bytes under a server-generated, non-filename-derived key linked to one document version. Bucket credentials stay server-side. Fetch/write is bounded; successful acceptance verifies the stored object's size and SHA-256 against the source version. An original is never overwritten by a re-import or client-controlled key. No public bucket/object URL; future PDF delivery must authorize owner + paper + version. Object write precedes DB commit because no cross-system transaction exists: on validation/DB failure, do not return success, remove the unreferenced object best-effort, and log a safe cleanup marker if removal fails. A DB-visible accepted record must not point at a missing/mismatched object; dependency failures return a safe retriable error rather than a paper row advertised as imported.

## 4. Google sign-in and session contract

1. Browser starts at `GET /auth/google/start` on the shared origin. FastAPI creates one-use, short-lived OAuth transaction values (`state`, PKCE verifier/challenge, `nonce`) bound to an `HttpOnly` host-only correlation cookie; authorize redirect uses the configured Google client and exact callback URI. An invalid/expired/replayed state, nonce mismatch, invalid issuer/audience/signature/expiry or failed token exchange creates no Researcy session and returns to a safe sign-in error state. Validate the Google identity with the provider's published keys; do not identify users by mutable email or trust an arbitrary redirect URL. Redirect after success is a fixed local Library URL.
2. On validated callback, upsert user by issuer + `sub`; generate a high-entropy opaque session and a separate CSRF secret. The browser receives only the raw session in a host-only `HttpOnly`, `SameSite=Lax`, `Path=/` cookie; `Secure` under HTTPS. PostgreSQL holds only a keyed lookup hash of the token (key kept outside DB), with expiration/revocation and a verifier for the session-bound CSRF secret. Google credentials are not application credentials and are not stored as a reusable browser session. No application JWT.
3. Issue a readable, host-only `SameSite=Lax`, `Path=/` CSRF cookie (`Secure` under HTTPS). Every cookie-authenticated state-changing request, including import and logout, copies it into `X-CSRF-Token`; FastAPI checks session binding and equality in constant time and rejects missing/mismatched values without side effects. Verify trusted `Origin` for state-changing browser requests as defense in depth. OAuth callback uses its own state/nonce/PKCE checks, not the application CSRF header. On logout revoke the server row, clear both cookies, then navigate to sign-in. A cleared cookie **alone** is not revocation.
4. `GET /api/me` returns safe profile fields and a request ID, not a session token. Authenticated requests fail after server-side revocation or expiry even if an old cookie is replayed. Session expiry is server-enforced; an expired session requires a fresh Google sign-in. Local HTTP development may use non-`Secure` host-only cookies only in an explicitly local profile; deployment requires HTTPS and secure cookies. No permissive production fallback.

## 5. Intake, validation and consistency

**arXiv:** Accept an arXiv ID or an `https://arxiv.org/abs/…` or `/pdf/…` URL, with optional `vN` suffix; reject other schemes, hosts, paths, ambiguous identifiers, fragments/credential-bearing URLs and malformed IDs. Normalize to a canonical ID; if unversioned and not already owned, resolve the official version before fetching its version-specific PDF. If an explicit `vN` is requested, fetch that version or fail safely if the official metadata/download cannot establish it. Construct official arXiv metadata/PDF requests server-side (never fetch a submitted URL verbatim), verify provider identity and final permitted URL, and persist the resolved version, source URL and PDF hash; do not infer a version from PDF bytes alone. Obtain title, authors, year and the original PDF only from the official arXiv source; no search/DiscoveryAgent or model call. Bound response size, redirects to allowlisted official arXiv hosts, and network time; upstream outage/429 produces a safe retriable error without a Library item. An unversioned repeat of an owned canonical ID returns the existing item and explicitly reports its stored version; a different explicit version returns `409`, with no new download, job or implicit replacement.

**Upload:** One multipart PDF file plus an idempotency key. Stream to a bounded temporary/private sink; reject over-limit data while receiving, regardless of declared `Content-Length`. Ignore the supplied basename as a storage path; sanitize it only for display. No client-supplied owner, source filter, ready flag or object key. Extract title from safe PDF metadata if usable, otherwise show a sanitized filename-derived title; unknown authors/year remain unknown, not invented. The server does not rely on a client-side file extension or MIME alone.

**Initial checks for either path, before queuing:** Verify PDF magic/signature and reported MIME consistency where supplied; enforce configured byte/page limits; reject corrupt or encrypted/password-protected PDFs; inspect extractable text across all pages within those bounds without executing embedded actions or JavaScript. Initial operating caps are **25 MiB and 100 pages**, configurable and subject to revision against representative documents; Q0 measured neither cap nor a universal text threshold. Reject a PDF with **zero** extractable text before queueing as image-only/unsupported. A nonzero but low-text document (initial screening signals: fewer than 200 characters in total, or fewer than half its pages having at least 40 characters) receives a persisted, visible low-text warning, not an automatic rejection; it may be accepted as `queued`, but is **not** presented as confirmed supported or `ready`. M2's full parser makes the final processing decision and may fail the item. Apply the same rules to arXiv and upload. Inspect in a non-root process with wall-time and memory limits; timeout/resource exhaustion is a safe rejection with no accepted item. M1 does no structural parsing/normalization. Signature/MIME failure, encryption, corruption, oversize, excess pages or zero text yields a specific safe error and **no** paper/version/job. Retain no rejected upload in the accepted original bucket.

**Acceptance transaction:** On an initially screened, privately stored PDF (including a warning-bearing document, if applicable), insert paper + immutable source version + persisted screening warning + `queued` job + idempotency outcome in one DB transaction. Return `202 Accepted` with paper ID, version ID, job ID, `queued` stage and request ID only after both object verification and commit succeed. This commits the original, **not** final PDF support or processing success. The source PDF and active version remain immutable; new processing versions are M2 territory. On the same owner/key/request digest, replay the stored resource identity without another download, object or job; same key with a different operation/content returns `409`. Concurrent requests must respect DB uniqueness and not publish duplicate jobs. A network disconnect after commit is recoverable via key replay or an owner-scoped Library read; without commit, no accepted paper is visible. If object-store compensation fails, an unreferenced private object is a recorded cleanup fault, never visible to another user or falsely reported as a successful import.

## 6. HTTP and UI state contract

Existing master route names stay unchanged. Authentication entry/callback/logout routes below are M1-local additions to the §15 API listing; the master does not prescribe their names. All JSON error responses use `{ "code": "STABLE_CODE", "message": "Safe actionable text", "request_id": "…" }`; never include secrets, raw provider responses, document text, or whether a foreign paper exists. Success responses include `request_id`. IDs are opaque server IDs, not ownership assertions.

| Route | Authorized observable contract |
|---|---|
| `GET /auth/google/start`, `GET /auth/google/callback` | Browser redirects through Google; safe success to Library or safe sign-in error; no JSON token or arbitrary redirect. |
| `POST /auth/logout` | Authenticated + CSRF; revoke current session before clearing cookies; subsequent old-token replay returns `401`. |
| `GET /api/me` | Current user profile; unauthenticated/expired/revoked `401`. |
| `GET /api/papers?search=…` | Owner-filtered list, server-side title/author search; return `{"papers":[],"request_id":"…"}` when empty. Each row: paper ID, title, authors, year, source, current stage, active version ID, resolved arXiv version when applicable, and persisted initial-screening warning when applicable; no foreign rows. |
| `GET /api/papers/:paperId` | Owner-filtered detail, source/processing stage, persisted screening warning and stored arXiv version when present; foreign and nonexistent IDs indistinguishable `404`, including malformed-but-well-formed identifiers that do not resolve. |
| `POST /api/papers/arxiv` | JSON `{"arxiv_id_or_url":"…"}` plus `Idempotency-Key`; `202` on new accepted queued item, `200` on existing owned canonical ID/key replay with **stored version**, `409` for key reuse with changed payload or explicitly requested different source version. Unversioned repeat never implies an update. |
| `POST /api/papers/upload` | Multipart `file` plus `Idempotency-Key`; `202` on accepted queued item, `200` on exact key replay, `409` on changed-content key reuse. |

For either import, a new `202` body is `{"paper_id":"…","document_version":"…","job_id":"…","stage":"queued","screening_warning":null,"request_id":"…"}`; `screening_warning` instead contains a safe code/message for accepted low-text input. An arXiv response also reports the resolved/stored arXiv version. An existing-item response returns the same identifiers, persisted warning and **actual persisted** stage rather than a fabricated new job. Other relevant statuses: `400` malformed arXiv ID/key, `401` missing/revoked/expired session, `403` missing/invalid CSRF, `404` foreign/nonexistent private paper, `409` conflicting arXiv version/key, `413` upload exceeds byte cap, `415` non-PDF MIME/signature, `422` corrupt/encrypted/too many pages/zero text or unusable source, `429` per-user import limit, `502/503` official arXiv or storage unavailable. Codes distinguish recoverable upstream failure from unsupported input without exposing internal details. Invalid/foreign IDs never read or return a PDF; authorization must run before any private object lookup. API contracts here are behavioral; exact OpenAPI field typing is settled in the post-approval implementation plan per master §15.

| Surface/state | Visible behavior and recovery |
|---|---|
| Sign-in idle, redirecting, OAuth failed, signed in, expired | Explicit Google action and progress; safe retry on callback failure; expired/revoked returns to sign-in without stale Library content. |
| Library loading, empty, populated, query-empty, load error | Loading feedback; empty state offers Add paper; title/author search changes the owner-filtered result; error keeps a safe retry with request ID, never a fabricated/foreign row. |
| Add paper idle, validating/uploading/downloading, accepted, accepted-with-warning, input error, upstream error | Exactly two choices; disable duplicate submission while in flight; accepted navigates/displays the persisted queued row. An accepted low-text PDF visibly warns that M2 processing may fail; it is not labelled supported or ready. Field-associated errors and explicit retry reuse the same idempotency key only for the same payload. |
| Queued row and detail | Title, available authors/year, source, stored arXiv version when present, persisted screening warning when present, and "Waiting for processing" stage from DB; no `ready` badge, functional Reader link, fake progress percentage or claimed parser output. An unversioned arXiv repeat shows its existing version. Future M2 stages/failure/retry render only when actually persisted. |
| Logout pending, signed out | Wait for server revocation success, then clear authenticated view; if request fails, show a safe error and do not claim logout succeeded. |

Keyboard traversal, visible focus, labelled forms/errors, restrained status announcements, responsive landing/auth/Library, no clipped controls or horizontal overflow at supported desktop widths, and readable unknown metadata follow master §§12–14 and 21. Do not add list/grid switching, source/year/sort filters or an M1 Reader placeholder presented as functional.

## 7. Four exit gates and evidence to record

`Verified` requires **all four** delivery-map gates, using the real running Next.js/FastAPI/PostgreSQL/MinIO path and recorded request IDs/artifact identities. Isolated automated checks support but do not replace observable acceptance; Q0 reports cannot satisfy an M1 gate.

1. **Two-user ownership isolation.** Sign in as separate real Google identities A and B (separate browser contexts). A imports one arXiv and one PDF; B's list/search cannot include either. B requesting each A paper ID by detail returns the same `404` code/body shape as a nonexistent ID; B cannot use A's idempotency key to obtain A's item. Probe that the private bucket disallows direct browser access and that the backend object lookup is guarded by owner + paper + version; an M1 PDF-serving endpoint is **not** required. Repeat with swapped owners. Record browser journey, redacted response codes/request IDs, DB owner FKs and private bucket access evidence; never include cookies/tokens or PDF text in reports. Exercise `401` without a session and `403` on missing/mismatched CSRF for both POSTs; no paper/object/job changes after rejection.
2. **Both import paths persist valid paper and original PDF.** Use official arXiv `1706.03762` (or an actually available supported ID) and a supported born-digital uploaded PDF. For each, observe `202`, matching owner-scoped paper/version/queued-job rows, private original object, PDF magic/size/hash equality with recorded source version; replay identical idempotency key and verify no second version/object/job. Exercise rejected fully image-only/encrypted/corrupt/oversized input and arXiv upstream failure: no accepted rows/jobs, no public original and safe errors. Separately submit a nonzero low-text PDF: if accepted, its warning persists across Library refresh, and neither UI nor API claims it is ready/supported. Re-import the same arXiv ID without a version: expect the stored version; explicitly request a different version: expect `409`, no replacement/download/job. A paper stays `queued`, never `ready`, without M2.
3. **Library states reflect real database state.** In the browser verify loading → empty → accepted queued row, owner-scoped title/author search and query-empty, persistent rows after refresh/new session for the same identity, unknown metadata display, and safe dependency error/retry. Cross-check displayed row/stage against committed DB record, including no phantom row after failed upload. No fake processing progression; browser keyboard/focus/responsive/overflow checks on M1 surfaces.
4. **Logout revokes the server-side session.** Capture the old opaque cookie securely for the probe; call CSRF-protected logout, verify row revoked in PostgreSQL and browser returns to sign-in. Replay the **old** cookie directly to `GET /api/me` and `GET /api/papers`: both `401`; a state-changing request with old cookie/header cannot create a paper. Another user's independent session remains valid. Record redacted HTTP statuses/request IDs and revocation row state; never publish token bytes.

Evidence record for each gate must name environment/command or browser journey, database/object-storage inspection, expected and observed outcomes, and failures. A failed gate leaves M1 at its prior status with blocker. Spec approval moves M1 and its M1-owned requirements to `Designed` only; an approved implementation plan later moves it to `Planned`; code without all four recorded gates can be `Implemented`, never `Verified`. Do not update the delivery map during review of this proposal.

## 8. Approval points and consistency review

**Owner-approved policy choices (this review):** Keep configurable initial operating caps of 25 MiB and 100 pages. Do **not** reject solely because fewer than half the pages have 40 characters; for nonzero low text, persist and display a warning, with M2 deciding final support. Reject a wholly image-only PDF before queueing. Re-importing an owned arXiv ID never silently changes the stored version; an explicitly different version returns `409` until M2 designs version creation/reprocessing. The 200-character and per-page signals are initial warning heuristics, not Q0-validated universal thresholds; check them against representative scientific PDFs during implementation before treating them as an acceptance-quality rule. These policy choices do not by themselves approve the entire child specification. Google OAuth client/secret, approved redirect URI, two real Google test identities and a private MinIO deployment are **execution prerequisites** for the later acceptance journey, not reasons to claim this design is implemented.

**Self-review against master/delivery map:** §4 and §17 require initial PDF rejection/warning; §8 requires atomic paper/version/job before `202`, while `JOB-01` worker reliability belongs to M2; §§12 and 15 require one Library, exactly two add options and existing `/api/papers` import paths; §16 requires PKCE/state/nonce, opaque server sessions, CSRF and 404 ownership behavior; §21 and delivery map require all four recorded M1 gates. No M1 `ready` publication, job worker, parser outputs, Qdrant, model route, ReaderAgent or M3–M5 behavior is promised. The future parser sandbox/full SEC-01 remains M2. This proposed document changes no master requirement and provides no M1 completion evidence.
